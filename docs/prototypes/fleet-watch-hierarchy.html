Semantik vor Optik

Was der Baum wirklich bedeutet

Profil ist oberste Trennung

Ein Repository unter „privat“ und „arbeit“ erscheint zweimal. Jede VM zählt genau einmal. Gruppen zeigen VM-Anzahl sowie blocked- und unknown-Zähler, keinen vermischten Gesamtstatus.

Worktree-Zugehörigkeit kommt von Git

Vorgabe für Umsetzung: Git-Metadaten identifizieren Repository und Hauptcheckout; Worktree-Pfade dürfen außerhalb liegen. Branch ist nur Label, nicht Identität. Hier sind diese Beziehungen erfundene Beispieldaten.

Hauptcheckout ohne VM bleibt sichtbar

„storefront“ hat nur aktive Worktree-Instanzen. Projekt bleibt als Elternknoten stehen; Hinweis „0 VM im Hauptcheckout“ erscheint bei Auswahl im Detailbereich. Ordner ohne Git bleiben eigenständige Projektgruppen.

Unbekannt heißt nicht beendet

VM-Status und Agent-Aktivität bleiben getrennt. Fehlende frische Telemetrie setzt Aktivität und Laufzeit auf unknown. Git-Erkennungsfehler sollen später auf exakte Ordnergruppen zurückfallen, nie Instanzen verstecken.

Kein Umbau der Startkonfiguration

Projekt- und Worktree-Pfade bleiben exakte Workspace-Identitäten. Gruppierung verändert weder Mounts noch Profile noch Startverhalten. Unterordner eines Checkouts müssten später separat gekennzeichnet bleiben.

Stabile Auswahl bei Aktualisierung

Vorgabe für Umsetzung: VM-Identität und Scrollposition behalten. Baum bleibt immer vollständig geöffnet. Neue VMs stehlen keinen Fokus. Endet ausgewählte VM, nächste Instanz im selben Workspace wählen, sonst Elternknoten mit Hinweis.

Selbstständige HTML-Prototypen, keine neuen CLI-Flags oder implementierten TUI-Funktionen. Fester Snapshot, keine echte Git-Erkennung und kein Polling. CPU/RAM = Limits; Version = Imagekatalog. Frühere Entwürfe: Projektlayouts ohne Profilhierarchie.
